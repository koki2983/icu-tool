# tools：公開前の確認と、追加した文の元

目的：作業した環境が消えても、同じ確認と追加ができるように、道具を残す。
読む人：このアプリを直す人（人でも AI でも）。
ゴール：`index.html` を直したら、下の確認を回してから公開する。

## 公開の手順
1. `index.html` を直す
2. `<script>` の中身を取り出して `node --check` で文法を確かめる
3. `確認/` のスクリプトを回す（下の表）。エラーとはみ出しが 0 であること
4. `python3 確認/stamp.py` で版の日時を付ける（`index.html` の `APP_BUILD`）
5. コミットして `main` に push。1〜2 分で本番に出る
6. 本番の URL を引数にして、もう一度 3 を回す

## 確認のスクリプト（Node ＋ Playwright。引数は URL。省くと手元のファイル）
| ファイル | 見るもの |
|---|---|
| t5.js | 直接リンク（#k= #c= #p=）12 本が開くか |
| fg.js | 追加した図（pf_ で始まるもの）の文字が、枠からはみ出していないか。図を 1 枚ずつ画像にする |
| d5.js | 指定した項目と薬剤各論が開くか、主な図のはみ出し、数（知識・用語） |
| pr.js | 全項目を開いて、薬の名前の併記と、画面のエラー |
| f1.js | 見出しの折りたたみ、見出しつきの直接リンク、すぐ報告の一覧、利用の記録 |
| s1.js | 照合の印、最近追加した項目、薬剤タブの見出しと絞りこみ |
| ck.js | チェック画面（#p=check）と、その中の ID |
| ex.js | 全項目の本文を JSON に書き出す（確認用の一覧のもと） |

## 元の文
`元の文/` は、`index.html` に入れた追加分の元（疾患、薬剤各論、図、折りたたみ、照合の印など）。
`index.html` が正で、ここは控え。直すときは `index.html` を直し、必要ならここも合わせる。

## してはいけないこと（理由つき）
- GitHub のトークンをリポジトリに入れない（公開リポジトリなので、誰でも読める）
- 患者さんを特定できる情報を入れない（アプリは公開されている）
- 固定 ID（`KID`）を変えない（チェックリストや直接リンクが切れる）
- 「当院の基準と医師の指示が優先」の一文を消さない（一般的な目安と、当院の決まりを取り違えさせないため）

## 確認の印と、更新の履歴（2026-11-13 に追加）

目的：医師・薬剤師が確認したあとに本文を直したとき、「確認済み」の印だけが残って読む人をだますことがないようにする。

1. `python3 tools/確認/stamp.py "今回の変更をひとことで"`：版の日時と、更新の履歴（`HIST`）を作り直す。ひとことは commit の題と同じにする。理由：履歴は git の記録から作るので、まだ commit していない今回の分は、ここで渡さないと 1 回おくれて出るから
2. `node tools/確認/verhash.js`：確認の印のある項目のうち、印のあとに本文が変わったものを一覧で出す（書きかえはしない）
3. `node tools/確認/verhash.js --write`：今の本文を「確認したときの本文」として控え直す（`VERH`）。確認の印を付けた・付け直したときだけ使う。ふだんの直しでは使わない。理由：使うと、「確認のあとに直した」ことが画面から消えるから

## 麻酔科の先生に配る紙（2026-11-13 に追加）

- 置き場所：`docs/確認用/麻酔科/`（お願い 1 つ＋チェック表 A〜G）
- 作り直し：本文を直したあとは、全項目を書き出して（`ex.js`）、数字の入った行と「すぐ報告」の行を抜き出し、`word_build_masuika.js` で Word にする。チェック表は、作った時点の版の本文（表紙に版の日時を印字）
- 作り直しの手順（2026-11-13 夜に追加。理由：行を抜き出す道具と QR の作り方がリポジトリになく、作り直せなかったため）
  1. `node tools/確認/ex2.js index.html /tmp/all.json`：全項目の本文を書き出す（`ex.js` と同じ中身。jsdom で動くので Playwright が要らない。`npm install jsdom` が要る）
  2. `python3 tools/確認/check_build.py /tmp/all.json /tmp/build`：`data.json` と「数字の行」のテキスト 3 つを作る。抜き出す行の決まりは、このファイルの先頭に書いてある。どの項目をどの表に入れるかは `check_parts.json`
  3. `node tools/確認/qr_build.js /tmp/build/data.json /tmp/build/qr`：QR コードの画像（`npm install qrcode` が要る）
  4. `word_build_masuika.js` を `/tmp/build` に置いて `node word_build_masuika.js`：`out/` に Word が 8 つ出る。`docs/確認用/麻酔科/` と `docs/確認用/` に置きかえる
  5. このコミットでは `stamp.py` を走らせない。理由：版の日時が変わると、表紙に印字した版とアプリの版がずれるから（本文は同じでも、見る人が迷う）
- 新しい項目を足したら `check_parts.json` にも ID を足す。足し忘れは、手順 2 の出力「どの表にも入っていない項目」に出る（解剖 6 つと出典は、わざと入れていない）
- アプリの確認モード：アドレスの最後に `#review` を付けて開く。指摘は見る人の端末の中だけに残り、「まとめてコピー」か「ファイルに保存」で取り出して送ってもらう

## 確認モードの指摘を、自動で Teams に集める（2026-11-15 に追加）

目的：見てくれる人が「送る」操作をしなくても、指摘が小山田に届くようにする。理由：送る操作を頼むと、ほとんど届かないから。

1. しくみ：確認モードで「指摘を残す」「指摘を消す」「この項目は問題なし」を押すたびに、その 1 件を Teams のワークフロー（受け取り口）に送る。届き先は、小山田の Microsoft アカウントで作ったチーム「ICUツール 指摘」の「一般」チャネル
2. 受け取り口の URL は index.html の `RV_HOOK`。ワークフローを作り直したら、ここを書きかえる。いたずらが来たときも、作り直して URL を替えれば止まる
3. 送れなかった分は端末の 'rvq' にためて、電波が戻る・画面に戻る・1 分ごと、に送り直す
4. 送る内容：項目・見出し・今の文・指摘・職種とお名前（任意）・端末の記号（4 文字）・版・時刻。患者さんの情報は扱わない
5. 画面と配布の紙に「自動で届く」と書いてある。黙って送る作りに変えない。理由：知らせずに集めると、見てくれる人の信用を失うから
6. テスト：`node tools/確認/review_auto_t.js <アプリのURL>`（受け取り口への送信は横取りして、実際には送らない）
